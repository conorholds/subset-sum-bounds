# Contributing

Bring one result that another person can inspect and reproduce. Small
improvements, corrections, independent checks, and scoped negative findings all
count. If you have an agent session available but no assigned question, start
with [autoresearch.md](autoresearch.md).

## Pick a question and coordinate

1. Read the [selected result](certificates/selected-result.json),
   [current status](docs/current-status.md), and the relevant
   [task](TASKS.md). Pin the commit you are building on.
2. Search open PRs, Issues, Discussions, and the relevant research directories.
   Compare the actual mathematical question, not just the title or random seed.
3. Use an existing task issue for a short scope and status update when it fits.
   Use Discussions for ideas, questions, and handoffs. A different seed alone
   is not a different research task. Independent checks are welcome; say what
   you will implement independently.

A claim is advisory, not a lock on a topic. Keep it concrete: the object or
family, changed assumption, expected artifact, and a rough checkpoint. Mark a
task available again when you stop. A useful local handoff is fine when you
cannot publish. Respect your user's account and publication permissions.

## Keep the claim small and complete

For numerical work, use exact decimal strings in witnesses. Supply the full
parameter tuple and pay for representation coverage, list generation, emitted
lists, visited pairs, preliminary search, checksum error, and final assembly.
Improving one filter moment does not by itself improve the whole algorithm.

For a proof or audit, identify the pinned source section and precise implication.
State hypotheses, the argument, what was checked, and what remains open. A
failed search is evidence about that search, not an impossibility theorem.
An interval certificate establishes the specified numerical inequalities; it
does not independently prove the complete Subset Sum algorithm.

## Package a numerical witness

Keep the initial research package and its retained witnesses intact. Put a new
investigation in `research/your-topic/` with:

- `README.md`: question, predecessor, result, argument, replay commands, limits,
  and one concrete next question.
- `witnesses.json`: exact designs and parameters in the existing witness schema.
  Give each witness a descriptive, unique identifier within the file.
- `CERTIFICATE.json`: a receipt generated by the shared checker, not edited by hand.
- Search code and concise discovery evidence when the construction depends on
  an experiment. Record seeds, evaluation limits, and environment details.

The initial source manifest remains the reference for this numerical model.
If you change a mathematical hypothesis or checker, explain the new model and
why the old certificate no longer suffices; include meaningful failure tests.
An incompatible model needs its own explicit verification path and review.

Generate a receipt from the repository root:

```sh
python research/filter-budgets/verify.py --witnesses research/your-topic/witnesses.json --output research/your-topic/CERTIFICATE.json
make check
git diff --check
```

`make verify` discovers numerical witness packages automatically. It validates
the committed receipt's input and checker hashes, then replays each package in
sequence. Fresh receipts can differ in timings and outward-rounded endpoints
across environments. Passing inequalities and source binding matter; byte-for-byte
equality of timing fields does not.

Do not overwrite a predecessor's coefficients or claim its contribution as your
own. Keep useful ablations and negative results, but omit large raw search logs,
private conversations, credentials, and environment directories. Proof-only
contributions can use a written argument and their own focused checks instead
of fabricating a numerical witness.

## Submit and review

Use a focused PR against `main`. The template asks for the claim, predecessor,
exact evidence, commands and outcomes, open obligations, and attribution.
Disclose substantial AI assistance and remain responsible for the submission.
One PR can be a correction or independent check without changing `alpha`.

GitHub verification is started manually by `conorholds`. In **Actions → Verify →
Run workflow**, keep the branch set to `main` and enter the PR number, or leave
it blank to check `main`. The run pins the selected commit, runs `make check`,
requires committed files to remain unchanged, and saves fresh interval receipts
for 14 days. Its **Verify certificates** result appears on that exact commit;
new PR commits need a new run. Contributors should run `make check` locally
before requesting verification.

Only maintainers promote the selected result. Promotion requires a fresh replay,
an explicit comparison of all costs, and review of the changed mathematical
implication by someone other than its author. Preserve the prior checkpoint and
credit the contributors whose pieces are composed. CI checks numerical and
repository consistency; scientific review is a separate requirement.

If a checker change invalidates old receipts, identify every affected package
and regenerate its evidence in the same PR. Do not loosen tolerances, remove
constraints, or replace a failing test just to admit a result. Run only the
relevant checks while iterating and one complete `make check` before submission.
Use one substantial replay at a time; avoid unattended, unbounded searches.

Contributions intentionally submitted for inclusion use the repository's
Apache-2.0 terms. Retain third-party attribution and licenses. Credit useful
independent and superseded work in the PR and, when integrated, in
[CONTRIBUTORS.md](CONTRIBUTORS.md).
